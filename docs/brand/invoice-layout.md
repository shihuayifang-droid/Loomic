# 发票抬头排版规范（BR-18 · 品牌泳道）

> 适用需求：BR-18「账单与发票抬头」。产品名固定 `HaHart`；开票主体由财务提供，存配置。
> 后端事实来源：`apps/server/src/billing/invoice-header.ts`（`formatInvoiceHeader`，工单 45DV / 45DW 已实现）。
> 本文件只规定抬头"长什么样、怎么排"；字段名一律沿用后端现有取值，不新增字段。

## 1. 行序规范

抬头是**竖排多行文本**，行序固定，与 `formatInvoiceHeader` 的输出顺序逐行一致。

| 序 | 行内容 | 出现条件 | 后端字段 |
| --- | --- | --- | --- |
| 1 | 产品名 | 抬头就绪（`ready=true`）时恒有 | `productName`，固定 `HaHart` |
| 2 | 开票主体 | 抬头就绪时恒有 | `company` |
| 3 | 税号 | 有值才出现 | `taxId` |
| 4 | 地址 | 有值才出现 | `address` |
| 5 | 电话 | 有值才出现 | `phone` |
| 6 | 开户行 | 有值才出现 | `bank` |
| 7 | 银行账号 | 有值才出现 | `account` |
| 8 | `可开具专用发票`（专票标记） | 仅 `complete=true` | 由 `complete` 推导，非独立字段 |

**为什么按这个顺序**：税务与财务核验抬头时，自上而下先看"主体 + 纳税人识别号"这组必不可少的对应关系，所以税号紧跟开票主体；地址 / 电话 / 开户行 / 银行账号属于专用发票才需要的开户信息，统一排在主体信息之后；专票标记作为收口行放在最后。这个顺序同时等于税务局查验习惯与后端输出顺序，任何落地场景都不得重排。

## 2. 标签写法

- 每行统一「标签：值」：使用**全角冒号**（U+FF1A），标签不加粗、不加编号、不加括号别名，也不写英文或缩写。
- 标签用固定字面，只有下面 7 个：

| 固定标签 | 对应后端字段 |
| --- | --- |
| `产品` | `productName` |
| `开票主体` | `company` |
| `税号` | `taxId` |
| `地址` | `address` |
| `电话` | `phone` |
| `开户行` | `bank` |
| `银行账号` | `account` |

- 唯一不带冒号的行是末行专票标记：整行只写 `可开具专用发票`，不加标签、不加冒号。

## 3. 缺项处理

缺项一律**整行不显示**：缺哪一项就不出现哪一行，绝不写 `无`、`N/A`、`未配置` 之类的占位文案。

理由：占位文案会被下游当成真实的抬头信息。抬头最终要印在票据、渲染在账单页、写进邮件正文；客户与财务拿到一行占位文案时，不能区分"这一项本来就不存在"和"这一项的值就是这几个字"，等于凭空造了一个值，也会让"抬头是否就绪"的判断失真。

与之配套的两条硬约束：

- 公司名缺失时整段抬头不输出（后端 `formatInvoiceHeader` 返回 `null`），由调用方提示"抬头信息不完整"，而不是渲染一张只有产品名的抬头。
- 四项专票信息不全时只省略对应行，不影响普通发票；此时 `complete` 随之为 `false`。

## 4. 何时追加「可开具专用发票」

- 仅当 `complete=true`（地址、电话、开户行、银行账号四项**全部**有值）时，在抬头最后追加这一行。
- 普通发票（`complete=false`）不显示该行；缺任意一项都不显示，也不写"可开具专用发票（信息不全）"这类变体。
- 产品名、开票主体、税号都不参与 `complete` 判定：税号有值不等于可开专票。

## 5. 三种落地场景的差异

同一份抬头，三种载体只允许在**呈现层**有差异，行序、标签、缺项规则完全一致。

| 场景 | 载体 | 排版原则（只写原则，不写具体样式值） |
| --- | --- | --- |
| ① API 纯文本 | `formatInvoiceHeader` 的返回值 | 原样多行文本，保留后端换行与行序；调用方只做展示，不重排、不合并、不补行；消费端用等宽字体呈现，便于逐位核对税号与账号 |
| ② 页面展示 | 账单 / 发票抬头区块 | 跟随品牌正文用字体，字号不小于正文可读下限、行距略宽于正文；标签弱化、值与标签左对齐同基线；整块保持竖排单列，不横排成多列、不只显示部分行；窄屏允许整块折行，不允许截断税号与账号 |
| ③ 邮件正文 | 账单通知邮件 | 用收件端普遍存在的安全字体，数字类行（税号、账号）用等宽字体；抬头以可复制文本给出，不渲染成图片；不依赖外部样式表与网络字体 |

差异只落在字体、字号、字距、对齐这几类呈现参数上，且都以"可读、可复制、可核对"为目标。

## 6. 示例（全部为占位，非真实信息）

```
产品：HaHart
开票主体：示例公司A
税号：示例税号A-0000-0000
地址：示例地址B
电话：000-0000-0000
开户行：示例银行C
银行账号：XXXX XXXX XXXX XXXX
可开具专用发票
```

缺项示例：只配置了开票主体与税号时，输出只有前三行（产品 / 开票主体 / 税号），其余行不出现，末尾也不出现专票标记。

## 7. 禁止事项

1. **不得在客户端硬编码抬头**：产品名以外的每一项都必须来自服务端配置（`HAHART_INVOICE_*`），前端与客户端不得内置任何抬头字面量，也不得自行拼接。
2. **不得缓存过期抬头**：抬头随配置变化，任何缓存必须能被动失效；不得把抬头写进前端构建产物或可长期缓存的响应；检测到配置变化后必须重新取值。
3. **不得把税号 / 银行账号写进日志**：这两项只允许出现在抬头渲染路径，日志、埋点、错误上报一律不含其值；定位问题时只记录"该字段存在与否"。
4. **不得新增字段或改字段名**：抬头只使用 `productName` / `company` / `taxId` / `address` / `phone` / `bank` / `account` 这些后端既有取值；任何新增字段先改后端与本规范。
